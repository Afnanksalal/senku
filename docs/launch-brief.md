## Scope interpretation

Keep the full learner platform in scope: Learn, Lab, Challenges, Discover, guest/account continuity, real-time collaboration, private sharing, custom approved-component pathways, offline local lessons and accessible scientific visualizations. Teacher Studio and public community follow later. Feature completeness, deployed availability and scientific validation are separate milestones.

Guest exploration does not imply anonymous access to costly cloud tools. Invitation-only budget controls must be enforced server-side. Decide whether guest collaboration is supported and how guest work migrates to an account. Shared links are not public-community publication; define viewer/editor roles, revocation and data visibility before shipping them.

Custom pathway composition does not mean arbitrary code or unrestricted biological workflows. Validate components, topology, units, stoichiometry, kinetics, solver capability and resource budgets. Preserve clear educational model status for user-composed networks.

## Collaboration acceptance implications

A shared room needs authoritative experiment/model identity and parameter state, participant permissions, reconnect behavior, conflict handling, and synchronized execution references. Do not imply all clients have completed the same run merely because a cursor or animation is shared. Detailed protocol and editing roles remain to be designed.

## Delivery honesty

Starting state is documentation only. A complete, scientifically reviewed production platform cannot credibly be guaranteed for the same day. Keep the requested target and full scope visible; report implemented, tested and pending features accurately. Do not relabel a partial build as the full platform or silently defer requested launch collaboration.
